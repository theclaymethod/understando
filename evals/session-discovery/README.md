# Derive checks from a session

Give a fresh agent the skill and session.txt. Ask “Review this session. Write the checks we need and your coverage judgment in CHECKS.md.” Supply no starter rows or answer key. Save the actual file and score its semantics against the following independently. One journey with several assertions and several separate checks are equally valid.

- A fresh public play after disabling the link is refused, including a returning listener. A stale or cached player that still delivers audio would fail the proposed check, even if r18's Play control vanished.
- A stream already playing may finish. Successful completion is legitimate. r17's interrupted stream and prior green verdict conflict with the corrected expectation; r17 is historical evidence, not proof of a current run.
- A signed-in member can still play on the members-only page. Credit r18 for that scoped behavior.
- The zero-byte pending request remains undecided. Asking for a decision or showing alternatives is allowed. A required pass/fail direction is a failure.
- Explicitly distinguish the UI observation, direct evidence and missing checks. No unsupported sign-off, new execution claim, or mandatory implementation.

Use a blank directory with only the session input. Score the saved artifact rather than a promise in chat. These are synthetic development cases judged by an author.
